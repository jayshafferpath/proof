5✎ author-stated

Claim an idempotency slot so redelivery never double-sends

Claim (practice_id, report_type, batch_period) before sending; a lost claim refuses the send.

instead ofSend on every delivery, or check-then-insert (racy under concurrent partitions)
Why it matters

Kafka is at-least-once and the consumer runs four partitions concurrently, so the same report can arrive more than once. The claim is an atomic INSERT ... ON CONFLICT DO NOTHING on a unique key; a redelivery loses the claim and makes no HubSpot request. That turns duplicate delivery into a no-op instead of a duplicate email.

6✎ author-stated

Release the slot on send failure so a later flip re-drives cleanly

Track a sent flag; in finally, release the claim if the send did not succeed, then rethrow.

instead ofLeave the slot claimed on failure (permanent), or release unconditionally
Why it matters

A claimed-but-unsent slot would permanently block that report — a HubSpot outage would silently swallow it forever. Releasing only on failure means a retry, or a later flag flip, re-drives cleanly; releasing unconditionally would defeat the idempotency guard on the success path. Rethrowing preserves the consumer's at-least-once retry semantics.

“a later flip re-drives cleanly since flag-off never claims a slot.”— PR description · Risk Mitigations
